# Source request policy

`validateConfiguration` produces an immutable configuration for the exact intake scope: `To == CurrentSeasonEndingYear` and the five ending years up to it (see [Decision: the current season](#decision-the-current-season)). It also carries a floor on the school index: an index that yields fewer than `minEligibleSchools` (300; about 360 are expected) eligible schools fails as `parse_failed` instead of queueing nothing, and reconciliation reports it (#115). A crawl may be restricted to a sample of it (see [Decision: crawl scope](#decision-crawl-scope)), never widened. It validates the provider, host allowlist, storage, parser versions, claim timeout, GET method, HTTPS scheme, manual redirects, and the request policy. The Fetcher validates the same request policy when constructed directly.

Requests are sequential per host, at least six seconds apart, and limited to ten starts per minute. The policy includes a whole-request timeout, bounded redirect count, maximum attempts, bounded exponential retry delay (a 404 or 410 uses its own longer one, `notFoundRetryBaseMs` 15 min doubling to `notFoundRetryMaxMs` 2 h, and shares `maxAttempts`), a response-byte limit (16 MiB by default), a maximum accepted `Retry-After` (24 hours by default), and optional cache freshness. The transport receives `timeoutMs` and `maxResponseBytes`; it must finish or cancel the socket before returning. The Fetcher renews the job claim while a request is active; a renewal that fails is retried on the next tick and once more when the request ends, and the response is discarded (`lease_renewal_failed`, a charged retry) only if the claim cannot be renewed then. Request ownership is released only when the socket settles. Redirects acquire ownership and apply pacing for each destination host parsed from the URL.

A fresh, checksum-verified cache entry can be reused without transport, except when the prior response declares `no-cache` or `no-store`. An upstream `max-age` can shorten the configured cache age. `no-cache` still permits a conditional request; `no-store` forces an unconditional request. Stale entries send available ETag and Last-Modified validators. A 304 requires a conditional request, reuses the verified immutable body, and records a new fetch without a new raw object. Cache hits also record a fetch with `cache_hit = true` and `reused_body = true` so their synthetic 200 status is distinguishable from a network response. A cache hit records the `fetched_at` of the body it reuses, so freshness is always measured from the last real request (a 200 or a 304): once `cacheMaxAgeMs` has passed since then, the entry is revalidated however many hits came between (#91).

A 429 with a valid `Retry-After` delays at least the minimum interval. Missing, invalid, or excessively long values stop for operator review; the worker never retries earlier than the provider requested merely to fit the configured cap. 429s have their own budget, `maxRateLimitAttempts` (5 by default): the response that reaches it stops the job for operator review (`rate_limit_cap`), and a reviewed `release_retry` restores the budget. 403 and recognized challenge pages stop for review. 5xx, socket resets, and timeouts use bounded exponential backoff and are the only responses charged to `maxAttempts`; waiting for a busy host and recovering an expired claim are never charged (see `JOB_LIFECYCLE.md`). Timeout uses the typed `transport_timeout` code while retaining the existing `retry_wait` or `permanently_failed` job states. TLS, DNS-policy, unsupported-encoding, and oversized-body failures stop for review rather than retrying.

The real transport uses HTTPS with certificate verification, manual redirects, no ambient proxy, identity content encoding, and a streaming byte limit. Before connecting, it resolves every address, rejects non-public addresses, and pins a validated address to the connection. It tries the validated addresses in turn (the family that last connected first), moving to the next only when a connection could not be made, so a host with no route for one address family still works; an address that has others behind it gets at most `connectTimeoutMs` (5 s) or half the remaining deadline, and the whole request still ends within `requestTimeoutMs`. The local TLS tests inject a loopback-only address policy and trust a test certificate; production defaults do neither. The fixture transport remains explicit in local mode. Worker mode still requires authorization and production parsers before crawling, and `createWorkerApplication` refuses a fake clock or a sleep that does not wait, so the request interval is always real time.

## Decision: crawl scope

**Status:** accepted (issue #78).

**Context.** The project's intake scope is fixed in form: every school whose index row has `To` equal to the current season's ending year, and each school's linked seasons over the five ending years up to it. It lives in `src/contracts/season.mjs` (`ELIGIBILITY_RULE`, `TARGET_YEARS_RULE`, `targetEndingYearsFor`). `validateConfiguration` requires exactly that predicate and window, and the authorization record's scope fingerprint includes the rules, so no configuration can silently change what a crawl covers. The #78 sample (two schools, one season) needs a narrower crawl without loosening those checks. Scope in a source contract also sits awkwardly with the README's "source-neutral" claim.

**Decision.**
- **The full scope stays a project contract, not configuration.** It is the scope the data contract and authorization describe, and it is provider-neutral in form: a predicate over index rows and a set of ending years. The source adapter only classifies and canonicalizes URLs; it carries no scope. Making the full scope configurable would bring back the silent-drift risk the foundation ruled out.
- **A sample is a restriction, not a replacement.** `crawlScope` (the `CRAWL_SAMPLE` environment variable, for example `{"schools":["/cbb/schools/duke/men/"],"endingYears":[2024]}`) names school-page paths and a subset of the target years. It is validated by `createCrawlScope` (`src/contracts/crawl-scope.mjs`), and the exact full-scope checks still run.
- **Discovery applies the sample.** The index still records every row's eligibility, so eligibility stays complete. But it queues a history page only for the sample's schools, and a history page queues seasons, and records unavailable coverage, only for the sample's years. Game logs and box scores follow from the sampled seasons as usual.
- **The scope is recorded with the data.** Each worker run records the scope in `crawl_scopes`, the latest row being the current one. The tracker, `npm run status` ("scope: SAMPLE, not complete coverage") and the reconciliation report (`scope`, with the season checks run against the sample's years) all show a sample as a sample. A store with no recorded scope was crawled under the full scope of 2022 through 2026, the scope every store had before the season was resolved.
- **A scope may only widen.** (A full scope also keeps the years already crawled when the season window moves on, #154.) A worker whose scope does not cover the store's recorded scope refuses to start. When the scope widens (the sample becoming the full backfill), the worker first runs discovery again over the stored index and history pages. That uses offline reprocessing, with no request, so the schools and years now in scope are queued before crawling resumes. Parsed pages are never refetched for it.

**Consequences.** The #78 sample and the full backfill can share one database: set `CRAWL_SAMPLE` for the sample, then remove it for the backfill. A sample can never be mistaken for complete coverage. Scope stays a reviewed code change for the project and a validated restriction for an operator.

## Decision: the current season

**Status:** accepted (issue #115).

**Context.** Eligibility was the literal `To == 2026` and the target seasons the literal 2022 through 2026. When Sports Reference adds the 2026-27 season, every active school's `To` becomes 2027, so a school index fetched after that finds no eligible school, and nothing in the crawl said that zero was wrong.

**Decision.**
- **The season is a calendar fact.** Sports Reference names a season by the year it ends in (`To` 2026 is 2025-26). The current season's ending year is the calendar year, plus one from 1 November (UTC), when games start: `seasonEndingYearAt` in `src/contracts/season.mjs`. Eligible schools have `To` equal to it, and the target seasons are the five ending years up to it.
- **It is decided when the school index is fetched.** A crawl takes days and restarts, so reading the calendar again on each start would change the answer across the rollover date: a stored 2026 index read on 2 November would find no school with `To` 2027. Instead a worker resolves the season when it starts, from the fetch time of the stored school index (`resolveSeasonEndingYear`); before the index has been fetched it is the season now. Reprocessing and review resolve it the same way. Every school observation records the season it was decided under, and reconciliation checks each decision against that season.
- **It can be pinned.** `CURRENT_SEASON_ENDING_YEAR` (for example `2027`) overrides the derivation, for when the site's index lists a different season than the calendar rule expects, for example because it added the next season early. It wins over the fetch time. The floor below is what tells an operator it is needed.
- **The rules are symbolic in the authorization record.** `config/personal-use.authorization.json` states `To == CurrentSeasonEndingYear` and `CurrentSeasonEndingYear-4..CurrentSeasonEndingYear`, so the record stays valid as the season rolls, with no yearly edit.
- **A floor makes a wrong season loud.** A school index that yields fewer than 300 eligible schools (about 360 are expected) fails as `parse_failed` and names the season it used, and reconciliation reports it, so an index the rule does not fit is never a quiet empty crawl.
- **The history parser keeps every linked season from 2022 on**, and discovery applies the window, so a window that has moved forward has its seasons.

- **A later season is added by a refresh (#154).** A store that already holds an index stays on the season it was fetched under: nothing reads the index or the histories again by itself. When the season rolls over, an operator runs `npm run review -- refresh-season` (see `OPERATIONS_RUNBOOK.md`). It makes no request. It puts the parsed school index and every parsed school history back in the queue as one recorded disposition (`refresh`, in `operator_dispositions`). While the index is waiting to be fetched, a worker resolves the season as the one now, not the stored fetch's, since the fetch that will replace it happens now. It records the widened scope, and does not run discovery over the stale stored index. A page whose refresh was requested replaces its accepted record when it differs, as an operator accept does, instead of being held as a conflict, and its child jobs are queued: the earlier fetch, raw body and revision stay on record. The request clears when the page is parsed. Only the index and histories are refreshed; season, game log and box score pages of finished seasons do not change, and refreshing a season in progress is out of scope.
- **The recorded full scope keeps its years.** After a rollover the window moves on (2023-2027 after 2022-2026) but the seasons already crawled are still in the store, so a full scope only gains years: the recorded scope is the union (2022-2027), and reconciliation checks what was crawled against it. A history is expected to have discovered the window of the season the index was read under; years outside it that an older history already discovered are allowed, not required.

**Consequences.** A fresh store picks up the current season on its own. A store that already has an index moves to a later season only through the refresh.
